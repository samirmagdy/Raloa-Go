# Media architecture

Media is a domain service, not a storage SDK exposed to Studio. The service owns authorization,
metadata, lifecycle transitions, processing jobs, and cleanup. Firebase Storage and Cloudflare R2
implement the same storage adapter contract and can be selected per environment or migration phase.

## Asset model

Each asset has separate records for:

- ownership: creator user and site;
- purpose: gallery, product, background, block, or avatar;
- original upload: immutable object key, MIME type, size, checksum, and provider;
- processed asset: normalized/optimized output;
- thumbnail: small preview output;
- metadata: dimensions, alt text, timestamps, and lifecycle state;
- delivery: CDN URL generated by the storage adapter, never a provider-specific URL assembled in a
  component.

Lifecycle is `pending_upload -> uploaded -> processing -> ready`, with `failed` and `deleted`
terminal/repair states. Processing is a durable idempotent job keyed by `media-processing:{assetId}`.
Deletion marks metadata first, then removes all object variants; cleanup can retry safely.

The service contracts live in
[`server/domains/media/contracts.ts`](../server/domains/media/contracts.ts), the orchestration is
in [`media-service.ts`](../server/domains/media/media-service.ts), and provider adapters are in
[`media-storage.ts`](../server/adapters/media-storage.ts).

## Provider boundary

Studio calls the media API and receives an asset contract. It does not import Firebase Storage,
Cloudflare R2, object keys, bucket names, upload URLs, or provider SDKs. Provider credentials stay
server-side. The API may later switch from multipart upload to signed upload URLs without changing
Studio’s domain model.

Originals and variants use distinct object keys and cache policies. CDN URLs are treated as delivery
projections; metadata remains authoritative in the media repository. Binary bytes are not stored in
PostgreSQL or Firestore.

## Persistence and jobs

PostgreSQL owns media metadata, ownership, lifecycle, and variant relationships. Firestore is only
a migration-compatible metadata adapter until the media domain cutover. Storage writes, processing,
thumbnail generation, CDN invalidation, and deletion are asynchronous where possible and use
idempotency keys, retries, and dead-letter handling. No database transaction spans an object-store
call.
